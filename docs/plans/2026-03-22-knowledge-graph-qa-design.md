# 知识图谱 + LangChain 问答系统设计（方案 B）

日期：2026-03-22  
范围：现有 Neo4j 知识图谱 + LangChain 编排 + 后续可扩展 RAG

## 1. 背景
- 现有知识图谱由 Excel 数据构建（`docs/知识图谱/data1.xlsx`、`docs/知识图谱/data2.xlsx`），数据结构以异常现象、原因、临时/长期解决办法为主。  
- 后端已具备异常分析、相似异常、方案推荐、全量异常等图谱接口，可作为问答系统的结构化基础。  
- 当前尚未准备大规模非结构化文档，因此系统应优先保证“图谱问答可上线”，再逐步演进到 RAG。

## 2. 目标
- 支持自然语言问题的结构化问答，并能接入 LLM 生成更自然的回答。  
- 采用 LangChain 作为后端的智能编排与 LLM 集成层。  
- 为后续三路检索预留架构：
  - 图查询
  - 关键词检索
  - 向量检索

## 3. 非目标
- 不做 LLM 直接生成任意 Cypher。  
- 不在本阶段引入复杂 Agent 或全自动 GraphRAG。  
- 不在缺少文档语料的情况下强行落地向量检索。

## 4. 架构概览
采用“图谱优先、LangChain 编排、RAG 渐进扩展”的模式：
- **图查询**：复用 Neo4j 固定模板查询。  
- **关键词检索**：对现有异常现象、原因描述、方案文本做轻量文本匹配。  
- **向量检索**：后续当文档与切片准备完成后接入。  
- **回答生成**：LangChain 封装 LLM，基于检索结果生成 grounded answer。

## 5. 组件与职责
- **问答 API（FastAPI）**：统一入口，暴露 `knowledge-qa` 能力。  
- **问题路由器**：判断问题偏图谱、偏文档、或混合。  
- **Graph Retriever**：调用 Neo4j 模板查询。  
- **Keyword Retriever**：在结构化文本字段上做补充召回。  
- **Vector Retriever**：后续基于 LangChain + embedding + vector store 接入。  
- **Fusion Layer**：合并、去重、排序、裁剪上下文。  
- **LangChain Answerer**：调用 LLM 生成回答；未配置时退回模板摘要。

## 6. 数据流
1) 用户问题进入问答 API  
2) 路由器输出 requested route  
3) 执行图查询与其他可用 retriever  
4) 融合事实片段与引用  
5) LangChain LLM 生成回答；若未启用则退回模板回答  
6) 返回答案、引用、warnings、debug

## 7. 检索策略
- **图查询优先**  
  - 异常编号/序号类问题 → `get_anomaly_analysis`
  - 相似问题 → `find_similar_anomalies`
  - 方案建议 → `recommend_solutions`
  - 全量与统计 → `get_all_anomalies` / 统计接口
- **关键词检索**  
  - 在 anomaly/cause/solution 文本字段上做轻量召回
  - 用于补足图查询未命中时的弱检索能力
- **向量检索**  
  - 当前不启用
  - 后续接入 SOP、手册、工单、点检文档后再落地

## 8. 降级策略
- Neo4j 不可用 → 返回 503  
- LangChain 未配置或依赖未安装 → 使用模板摘要回答  
- 向量/文档检索未接入 → 明确返回“当前仅基于知识图谱事实”  
- 全部未命中 → 提示补充异常编号、产线类型、SOP/手册关键词

## 9. 运维与安全
- LLM API Key 仅通过环境变量配置。  
- 日志记录请求摘要、路由、命中数、耗时，不记录大段原文。  
- 保持“不让 LLM 直接自由拼接查询”的约束。

## 10. 里程碑
1) LangChain LLM 接入 + 图谱问答稳定化  
2) 关键词检索补充召回  
3) 文档切片规范与 embedding 管线  
4) 向量检索接入，形成完整 RAG

## 11. 风险与开放问题
- 当前缺少大量非结构化文档，RAG 的文档侧收益有限。  
- 模型与 embedding 供应商尚未最终确认。  
- 关键词检索与图查询的融合排序仍需迭代。
