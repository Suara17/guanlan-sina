### 常见坑 1：私钥有口令

这把 `es.pem` 有口令，第一次连接时会提示输入。输入正确口令后即可登录。

### 常见坑 2：OpenSSH 报私钥权限过宽

Windows 上这把私钥经常会触发：

```text
WARNING: UNPROTECTED PRIVATE KEY FILE!
Permissions for 'C:\Users\forzr\es.pem' are too open.
```

这时候不要怀疑人生，问题不是密钥坏了，是 Windows ACL 太恶心。

最稳的办法：
1. 不直接折腾原始 `es.pem`
2. 先把私钥内容喂给 `ssh-agent`
3. 再让 `ssh` 走 agent 登录

PowerShell 可直接这样做：

```powershell
$env:SSH_ASKPASS_REQUIRE = "force"
$env:DISPLAY = "dummy:0"
Get-Service ssh-agent | Set-Service -StartupType Manual
Start-Service ssh-agent
Get-Content "C:\Users\forzr\es.pem" -Raw | ssh-add -
ssh root@116.62.78.162
```

说明：
- `ssh-add -` 是从标准输入读私钥内容，能绕过 OpenSSH 对私钥文件 ACL 的狗脾气检查
- 执行 `ssh-add -` 时会要求输入私钥口令
- 成功后再执行 `ssh root@116.62.78.162` 就行

### 快速检查服务器是否在线

## 九、服务持续运行说明

### 自动启动机制
- Docker 容器设置了 `restart: unless-stopped` 策略
- 服务器重启后，容器会自动重新启动
- 除非明确执行 `docker compose down` 停止，否则服务会一直运行

### 可能导致服务中断的情况

| 情况 | 影响 | 解决方案 |
|-----|------|---------|
| 服务器重启 | 短暂中断，自动恢复 | 无需操作，容器自动重启 |
| Docker 服务重启 | 短暂中断 | `systemctl restart docker` |
| 容器崩溃 | 自动重启 | 检查日志排查原因 |
| 内存不足 | 可能被 OOM 杀掉 | 监控服务器资源 |
| 阿里云欠费 | 服务停止 | 及时充值 |

### 手动管理命令

```bash
# 停止所有服务
docker compose -f docker-compose.yml -f docker-compose.prod.yml down

# 启动所有服务
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

# 重启所有服务

### 2026-03-25 生产内存止血与 openclaw 清理

**处理目标：**
- 查看服务器内存占用并清理无关常驻进程
- 处理 `openclaw` 反复自启动问题
- 下调 `backend` 与 `neo4j` 的内存占用，避免小规格机器反复顶满

**处理前状态：**
- `free -h` 显示内存总量 `3.4Gi`
- 初始实测已用约 `3.2Gi`，空闲仅 `114Mi`
- `openclaw-gateway` 单进程占用约 `514MiB`
- `guanlan-sina-backend-1` 占用约 `1.316GiB`
- `guanlan-sina-neo4j-1` 占用约 `554.9MiB`

**定位结果：**
1. `openclaw` 不只是普通进程，实际有两条自动拉起链路：
   - 系统级：`openclaw-watchdog.service` + `openclaw-watchdog.timer`
   - 用户级：`root` 的 `systemd --user` 服务 `openclaw-gateway.service`
2. `openclaw-gateway.service` 配置里有：
   - `Restart=always`
   - `NODE_OPTIONS=--max-old-space-size=4096`
3. 生产后端镜像启动命令在 `backend/Dockerfile` 里写死了 `--workers 4`
4. `docker-compose.yml` 中 Neo4j 内存配置原为：
   - `NEO4J_dbms_memory_pagecache_size=512M`
   - `NEO4J_dbms_memory_heap_initial__size=256m`
   - `NEO4J_dbms_memory_heap_max__size=512m`

**本次实际处理：**
1. 停掉并禁用系统级 `openclaw-watchdog.timer/service`
2. 停掉并禁用 `root` 用户级 `openclaw-gateway.service`
3. 将 `~/.config/systemd/user/openclaw-gateway.service` 挪走后执行 `daemon-reload`
4. 调整生产配置：
   - `backend/Dockerfile`：改为 `fastapi run --workers ${WEB_CONCURRENCY:-2} app/main.py`
   - `docker-compose.yml`：为 backend 注入 `WEB_CONCURRENCY=${WEB_CONCURRENCY:-2}`
   - `docker-compose.yml`：将 Neo4j 内存下调为：
     - `pagecache=256M`
     - `heap initial=128m`
     - `heap max=256m`
5. 重建并重启 `backend`、`neo4j`
6. `prestart` 仍因管理员重复初始化失败，因此继续沿用：
   - `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --no-deps backend`

**处理后结果：**
1. `openclaw-gateway.service` 状态已变为：
   - `is-enabled -> not-found`
   - `is-active -> inactive`
2. 后端进程已按新配置运行，实际为 `2` 个 worker
3. `backend` 健康检查恢复正常
4. `curl http://127.0.0.1:8000/api/v1/utils/test/ping` 返回 `200`

docker ps

# 2. 停掉无关容器，避免内存和磁盘被吃光
docker stop mcp-boss-zp guanlan-sina-adminer-1 guanlan-sina-frontend-1 guanlan-sina-backend-1

# 3. 暂存服务器本地脏改动后拉最新代码
cd /root/guanlan-sina
git stash push -u -m "pre-deploy-20260324"
git config --global http.proxy socks5://127.0.0.1:1080
git config --global https.proxy socks5://127.0.0.1:1080
git fetch origin
git checkout main
git pull --ff-only origin main

# 4. 用缓存重建前后端

export COMPOSE_DOCKER_CLI_BUILD=1

docker compose -f docker-compose.yml -f docker-compose.prod.yml build frontend

# 5. 启动数据库和 Neo4j
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d db neo4j

# 6. prestart 会因 admin 重复初始化失败，后端需跳过 prestart 启动
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --no-deps backend
docker restart guanlan-sina-frontend-1
```

**这次踩到的坑：**

| 问题 | 原因分析 | 解决方案 |
|------|---------|---------|
| SSH 登录卡住或报私钥权限过宽 | Windows OpenSSH 对 `es.pem` 的 ACL 检查很烦 | 用 `ssh-add -` 从标准输入加载私钥，再 `ssh` 登录 |
| 后端首次重建失败 | 磁盘空间不足，卡在 `libtorch_cpu.so` 解层 | 删除无关镜像和无关容器后再重建 |
| `prestart` 失败 | 服务器已有 `admin` 用户，重复初始化撞唯一键 | 跳过 `prestart`，直接 `up -d --no-deps backend` |
| 服务器直连 Hugging Face / OpenAI 不稳定 | 国内网络限制 | 尽量使用本机缓存和本地持久化，不要依赖在线下载 |
| 知识问答本地模型离线加载不稳定 | `jina` 模型依赖动态代码与本地缓存路径兼容性一般 | 优先补齐本地缓存目录和挂载路径，再继续排查 |

**当前结果：**
1. 前端 `3000` 和后端 `8000` 已恢复访问
2. 基础接口已通：`/api/v1/utils/test/ping`
3. 知识问答接口可返回结果
4. 但远程服务器上的“本地模型 + Chroma 完整检索链路”仍需继续收尾，不能算完全闭环

**经验总结：**
1. 这台服务器是小鸡配置，部署前先看 `free -h` 和 `df -h`，别一上来就 build
2. 构建前先停无关容器、清无关镜像，比瞎加 swap 现实得多
3. 远程知识问答不要指望服务器临时下载模型，最好从本机缓存拷过去
4. `prestart` 在已有库数据的环境里不靠谱，看到重复建管理员报错别发愣，直接跳过

**更新内容：**

- 更新文件: `LandingPage.tsx`, `AboutUs.tsx`

| 问题 | 原因分析 | 解决方案 |
|------|---------|---------|
| xray代理连接超时 | 代理服务不稳定，TLS握手失败 | 重试多次后代理恢复正常连接 |
| git pull失败（本地更改冲突） | 服务器上有未提交的本地文件修改 | 使用 `git stash` 暂存本地更改后再拉取 |
| vite构建权限错误 (exit code: 126) | 服务器上存在残留的 `node_modules` 目录，导致Docker构建时权限冲突 | 删除服务器上的 `frontend/node_modules` 和 `frontend/dist` 目录 |

**关键命令记录：**

```bash
# 1. 配置代理并拉取代码
git config --global http.proxy socks5://127.0.0.1:1080
git config --global https.proxy socks5://127.0.0.1:1080
git stash && git pull origin 20260212

# 2. 清理残留文件（重要！）
rm -rf /root/guanlan-sina/frontend/node_modules /root/guanlan-sina/frontend/dist

# 3. 重新构建前端
docker compose -f docker-compose.yml -f docker-compose.prod.yml build frontend

# 4. 启动服务
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d frontend
```

**经验总结：**

2. **代理稳定性**：xray代理可能不稳定，需要多次重试或等待恢复
3. **本地更改处理**：使用 `git stash` 可以安全地暂存本地更改，避免强制覆盖
